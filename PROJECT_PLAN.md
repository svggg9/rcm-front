# План проекта RCM

## Главный фокус

Сначала довести фундамент маркетплейса: товарную модель, заказы, доставку, оплату, модерацию и базовый UX. После этого расширять рекомендации, аналитику, отзывы и более сложные сценарии.

Сейчас отдельный важный фокус - дизайн-система: токены, общие компоненты, единые паттерны карточек, форм, кабинетов, подборок и мобильных сценариев.

## Приоритеты

Перед запуском отдельный ручной чеклист живет в `PRELAUNCH_TESTING_PLAN.md`. Его нужно пройти на test CDEK/TBank/mock, а затем повторить ключевые сценарии на production-like конфиге.

### 1. Product -> Colorway -> SKU

Необходимость: 10/10

Фундамент товарной модели. Базовая структура уже есть в backend: `ProductColorway`, фото варианта, варианты товара, необязательный размер, необязательный "Артикул продавца" и числовой SKU. Дальше задача не "создать с нуля", а стабилизировать модель, UI и сценарии редактирования.

Что важно:

- довести связь товар -> вариант/цвет -> размеры/остатки/фото до понятного production-flow;
- проверить, что список товаров, карточка товара, предпросмотр и админка используют одно и то же главное фото;
- не показывать пустые технические черновики в общем списке товаров;
- добавить очистку заброшенных черновиков;
- позже перейти к временной загрузке фото через `uploadSessionId`, чтобы не создавать товар только ради загрузки изображений.

### 2. Нормальные статусы заказа, доставки и оплаты

Необходимость: 10/10

Базовое разделение уже есть в backend: `OrderStatus`, `PaymentStatus`, `DeliveryStatus`. Дальше нужно привести статусы, названия, цвета бейджей и переходы между состояниями к единой бизнес-логике.

Текущие backend-статусы:

- заказ: `NEW`, `CONFIRMED`, `PROCESSING`, `SHIPPED`, `COMPLETED`, `PAID`, `CANCELED`;
- оплата: `PENDING`, `PAID`, `FAILED`, `REFUNDED`;
- доставка: `PENDING`, `READY_FOR_SHIPMENT`, `IN_TRANSIT`, `DELIVERED`, `RETURNED`, `CANCELLED`, `READY_FOR_PICKUP`.

Что доделать:

- убрать неоднозначность между `OrderStatus.PAID` и `PaymentStatus.PAID`;
- решить финальную карту статусов для покупателя, селлера и админа;
- зеленые бейджи использовать только для финальных успешных статусов;
- серые бейджи использовать для нейтральных рабочих статусов;
- статусы доставки подтягивать из интеграции, а не править вручную там, где это возможно.

### 3. СДЭК как полноценная интеграция

Необходимость: 9/10

СДЭК уже подключен как delivery provider: расчет тарифов, ПВЗ, courier/pickup flow, хранение quote/shipment, sync-сервисы. Дальше нужно довести интеграцию до полноценного production-сценария.

Что осталось:

- создание реального отправления после заказа;
- стабильная работа с трек-номером;
- обновление статусов по расписанию или webhook;
- отмена отправления;
- корректная обработка ошибок провайдера;
- расчет по реальным весу и габаритам товаров, а не только default-пакету;
- удобная диагностика для админа/селлера.

Важно помнить по checkout:

- Россия остается страной по умолчанию;
- ПВЗ пользователь выбирает каждый раз, адрес ПВЗ не запоминаем как обычный адрес;
- курьерский адрес не должен перетираться после заказа через ПВЗ;
- при смене города очищаются адрес, квартира, этаж, домофон;
- подсказки адреса/города закрываются кликом в свободную область;
- лоадерные тексты типа "Ищем адрес", "срок рассчитывается", "рассчитываем" не показываем, чтобы UI не прыгал;
- сами цена и срок доставки должны отображаться, когда расчет готов.

### 4. Telegram-уведомления

Необходимость: 8/10

Для MVP очень полезно и быстро делает систему "живой".

Текущее состояние: базовый backend-flow подключен.

Что уже есть:

- `TelegramNotificationService` умеет отправлять сообщения напрямую в Telegram или через отдельный `notification-gateway`;
- отдельный `notification-gateway` принимает `POST /telegram/send`, проксирует Telegram webhook через `POST /telegram/webhook`, проверяет bearer/secret и маскирует секреты в логах;
- backend-конфиг поддерживает `TELEGRAM_ENABLED`, `TELEGRAM_DELIVERY_MODE=DIRECT|GATEWAY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_ADMIN_CHAT_ID`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_GATEWAY_URL`, `TELEGRAM_GATEWAY_SECRET`;
- у пользователя есть поля привязки Telegram: `telegram_chat_id`, `telegram_user_id`, `telegram_username`, `telegram_link_token`, `telegram_link_token_expires_at`, `telegram_linked_at`;
- продавец может получить ссылку привязки через `/api/profile/telegram/link`, проверить статус через `/api/profile/telegram`, отвязать через `DELETE /api/profile/telegram`;
- Telegram webhook `/api/telegram/webhook` принимает `/start seller_<token>` и сохраняет chat id пользователя;
- админ может отправить тестовое уведомление через `/api/admin/telegram/test`;
- админ получает уведомления о новой заявке продавца, новом заказе и товаре, отправленном на модерацию;
- селлер получает уведомления о новом заказе и об одобрении заявки, если Telegram привязан.

Что осталось:

- добавить UI в кабинете селлера для подключения/статуса/отвязки Telegram;
- добавить UI/кнопку в админке для тестового Telegram-уведомления;
- подключить уведомления по оплате заказа, проблемам доставки и важным изменениям статусов;
- решить финальную production-схему webhook URL и secrets для `notification-gateway`;
- добавить админскую диагностику последней ошибки/статуса отправки.

Production-доработки:

- ввести outbox для уведомлений: тип события, получатель, payload, статус, количество попыток, последняя ошибка, `nextRetryAt`;
- добавить retry/backoff, чтобы временные сбои Telegram или `notification-gateway` не теряли важные события;
- хранить историю отправок и показывать последнюю ошибку/статус в админке;
- типизировать notification events, чтобы вместо набора точечных методов был понятный список событий и получателей;
- добавить события оплаты, возврата, доставки, проблем доставки и смены важных статусов заказа;
- дать селлеру UI подключения Telegram в кабинете: подключить, проверить статус, отвязать, показать username и время привязки;
- дать админу UI для тестовой отправки, просмотра статуса Telegram-конфига и диагностики последней ошибки;
- для `notification-gateway` добавить rate limiting, более подробный `/health`, базовые метрики и понятные structured logs;
- не блокировать бизнес-операции ошибками Telegram: уведомления должны деградировать мягко и уходить в retry;
- продумать идемпотентность событий, чтобы один заказ/статус не отправлялся несколько раз при повторной обработке.

#### Комиссия, доставка и ledger

Финансовый ledger обязателен. Все деньги и обязательства должны раскладываться по событиям, иначе нельзя будет понять экономику мультиселлер-заказа, субсидии доставки, возврата, seller debit и выплаты селлеру.

Базовые правила v1:

- комиссия платформы по умолчанию: `20%` от суммы товаров без доставки;
- индивидуальная комиссия задается на уровне селлера;
- селлеру выплачивается `itemsSubtotal - commission - sellerDebits`;
- покупатель в checkout видит одну доставку на весь заказ, даже если внутри несколько селлеров;
- на первом этапе ограничить максимальное количество селлеров в одном checkout, ориентир: `3`;
- если в корзине больше лимита селлеров, попросить покупателя оформить часть товаров отдельным заказом;
- формула доставки для покупателя: `самая дорогая доставка + 50% остальных доставок`;
- максимальная субсидия доставки: `commissionTotal / 2`;
- если субсидии не хватает, доставка покупателя увеличивается до уровня, при котором RCM не уходит в минус по прямой доставке;
- при risk-покупателе субсидия отключается, покупатель видит фактическую сумму доставок.

Ledger-события:

- `COMMISSION_ACCRUED`;
- `BUYER_DELIVERY_FEE`;
- `DELIVERY_COST_FORWARD`;
- `DELIVERY_SUBSIDY`;
- `DELIVERY_COST_RETURN`;
- `REFUND_ITEM`;
- `REFUND_DELIVERY`;
- `SELLER_DEBIT`;
- `SELLER_PAYOUT`;
- `ACQUIRING_FEE`.

Возвраты и ответственность:

- при обычном отказе покупателя после передачи в доставку доставку покупателю не возвращаем;
- юридически закрепить в пользовательской оферте/правилах, что покупатель отвечает за фактические расходы доставки и возврата при отказе после передачи заказа в доставку;
- при полном возврате по браку/вине селлера доставку покупателю возвращаем;
- при частичном возврате доставку возвращаем только по отдельному решению, по умолчанию не возвращаем;
- при браке/вине селлера обратная доставка должна попадать в `sellerDebit`;
- субсидии и логистические убытки первого этапа можно покрывать как cost of growth, но обязательно считать в ledger.

Risk-правила покупателя:

- считать `refusalRate`, `returnRate`, количество отказов, сумму отказов и логистический убыток RCM;
- базовый MVP-порог: `refusalRate > 50%` при минимум `2` заказах/доставках;
- для risk-покупателя отключать субсидию доставки и показывать фактическую доставку;
- оставить ручной флаг блокировки/разблокировки доставочной субсидии админом.

#### ProductShowcase

Для подборок уже используется общий компонент `ProductShowcase`.

Компонент имеет два режима:

1. `variant="grid"`

Для главной и editorial-подборок.

Поведение:

- заголовок слева;
- кнопка справа в уровень с заголовком;
- дефолтный текст кнопки: "Начать шопинг";
- показывать до 4 товаров;
- desktop: сетка 4 товара;
- mobile: горизонтальный скролл, 2 карточки в зоне видимости, снизу индикатор;
- без стрелок.

2. `variant="carousel"`

Для карточки товара, корзины, рекомендаций.

Поведение:

- заголовок;
- дефолтный текст кнопки, если есть ссылка: "Показать больше";
- товаров может быть больше, например до 12;
- desktop: карусель со стрелками;
- mobile: горизонтальный скролл;
- используется для:
  - "Еще от бренда";
  - "Вам может понравиться";
  - будущих рекомендаций.

`ProductCarousel` оставить нижнеуровневым компонентом, который отвечает только за горизонтальную прокрутку товаров. Он не должен сам быть полноценной секцией страницы.

Текущие подключения:

- главная: `ProductShowcase variant="grid"`;
- карточка товара: `ProductShowcase variant="carousel"` для "Еще от бренда";
- корзина: `ProductShowcase variant="carousel"` для "Вам может понравиться".

## UI-договоренности

### Общий стиль

- UI должен быть простым, понятным и спокойным.
- Основные цвета: черный, белый, золото.
- Цветные кнопки делать мягкими, не слишком резкими.
- Серые/золотые скелетоны не использовать там, где они выглядят грязно. Скелетоны должны быть простыми, светлыми, без лишних бордеров.
- Не показывать лишние поясняющие тексты, если поле и подсветка уже объясняют проблему.

### Цветовые токены

Золотая палитра:

- `--gold: #b08d57` - основной золотой акцент;
- `--gold-muted: #a89066` - приглушенный золотой для тонких UI-акцентов;
- `--gold-deep: #7a613a` - глубокий золотой/бронзовый для более контрастных деталей, например знака рубля;
- `--warning: #8a6a2f` - статусный warning, не использовать как брендовый gold без причины.

Семантические цвета:

- success: `#216a43`;
- warning: `#8a6a2f`;
- danger: `#9b2c2c`.

Черно-серая палитра пока требует чистки. В коде еще используются старые aliases `--content-primary`, `--content-primary-hover-label`, `--content-primary-hover-icon`, `--input-border-color`.

Предлагаемый компактный вариант:

- `--black: #111111` - сильный черный, кнопки, активные бордеры, иконки;
- `--text: #242424` - основной текст;
- `--muted: #6f6f6f` - вторичный текст;
- `--line: #d6d6d6` - тонкие линии и бордеры;
- `--surface: #f7f7f7` - светлый фон блоков/медиа;
- `--surface-hover: #f2f2f2` - hover-фон.

Кандидаты на удаление/объединение:

- `--input-border-color` удалить, не используется;
- `--content-primary` заменить на `--text`;
- `--content-primary-hover-label` заменить на `--black`;
- `--content-primary-hover-icon` заменить на `--black`;
- `--soft` заменить на `--surface`.

### Поля и формы

- Названия полей должны быть внутри поля сверху слева, а не только плейсхолдером.
- Если поле заполнено, название все равно должно быть видно.
- Обязательные пустые поля подсвечивать бледно-золотой заливкой.
- При фокусе золотую заливку убирать.
- Ошибки лучше показывать подсветкой поля, без лишних текстов типа "Выберите категорию".
- При ошибке сохранения скроллить к первой ошибке.
- В числовые поля запрещать буквы.
- Вес и габариты должны принимать десятичные значения: `11.07`, `11,07`.
- Цена должна форматироваться пробелами: `10 000`, `2 600`.
- Знак рубля должен быть справа от введенной суммы, а не в названии поля.

### Типографика

В проекте уже есть базовая шкала текстовых стилей. Ее нужно распространять на страницы вместо локальных размеров/весов.

Текущие роли:

- `textDisplay`: 56px, line-height 1, weight 400;
- `textPageTitle`: 40px, line-height 1.1, weight 400;
- `textSectionTitle`: 28px, line-height 1.15, weight 400;
- `textTitle`: 20px, line-height 1.25, weight 400;
- `textBody`: 14px, line-height 1.4, weight 400;
- `textSmall`: 13px, line-height 1.4, weight 300;
- `textCaption`: 12px, line-height 1.3, weight 300;
- `textPrice`: 14px, line-height 1.2, weight 300;
- `textButton`: 13px, line-height 1.2, weight 500;
- `textMicro`: 10px, line-height 1, weight 400.

Важно:

- letter-spacing держать `0`;
- заголовки не делать жирными без причины;
- цены держать легкими по весу, знак рубля можно выделять `--gold-deep`;
- новые страницы сначала собирать на этих ролях, а не подбирать размер вручную.

### Кнопки

- Разработать нормальную систему стилей кнопок в дизайн-системе.
- Нужны понятные варианты: primary, secondary, action, destructive, muted, modal action.
- Состояния должны быть едиными: default, hover, active, disabled, loading, saved/success.
- Для destructive/action-кнопок использовать мягкие цвета и черный/серый бордер, без резкой заливки.
- В модалках кнопки чаще делать двумя равными колонками на всю ширину.
- Текст кнопок вынести в отдельный типографический стиль, чуть плотнее обычного текста.
- Не решать стиль кнопок точечно на каждой странице, а постепенно свести к общему компоненту.

### Иконки

- Сейчас часть интерфейса использует текстовые символы вроде `>` или `+/-`.
- Нужно завести единый набор SVG-иконок в проекте и постепенно заменить временные текстовые символы.
- В первую очередь заменить:
  - стрелки перехода в карточках заказов/товаров;
  - плюс/удаление в формах вариантов;
  - стрелки dropdown;
  - контролы галереи;
  - иконки sidebar/header.

### Dropdown / Combobox

- Общие компоненты уже есть: `FormSelect` и `FormCombobox`.
- Дальше нужно не создавать новые локальные dropdown, а переиспользовать эти компоненты.
- Стиль: белый фон, тонкая серая рамка, обычный нежирный шрифт.
- Стрелка должна плавно поворачиваться при раскрытии.
- Раскрытый список должен быть аккуратным, без тяжелых бордеров и лишних разделителей.
- Для обязательных dropdown не должно быть варианта оставить пустым.
- Для опциональных значений можно давать "Без размера", "Без цвета" и похожие варианты.
- Для категории, размера, цвета/варианта можно разрешить ввод своего значения с последующей модерацией.

### Checkout

- Checkout должен быть одним понятным flow: пользователь заполняет данные и внизу подтверждает заказ.
- Не нужно отдельно подтверждать каждый блок.
- Правая summary-секция должна быть аккуратной, немного шире, без лишних промокодов и лишних "бесплатно".
- Главную форму держать ближе к центру, summary сбоку.
- Кнопки способов доставки/оплаты должны быть легкими, без лишнего текста.
- Активный переключатель: черная точка/кружок с белой галкой.
- Блоки "Доставка", "Получатель", "Оплата" приводить к одному стилю.

### Seller cabinet

- Общие компоненты уже есть: `CabinetSidebar` и `CabinetTabs`.
- Sidebar: ширина около 260px, кнопки во всю ширину, без лишних внешних отступов между пунктами.
- "Продавец" заменять названием магазина.
- "Кабинет продавца" можно делать золотым, но без лишней декоративности.
- Онбординг можно закрыть крестиком, если магазин готов.
- Карточки заказов открываются по клику, отдельную колонку "Действия" не показывать.
- В заказах полезно показывать фото товаров, сумму, статус, дату, покупателя, количество.
- Статусы должны иметь логичные цвета: подтвержденный не должен быть золотым просто потому что красиво.

### Seller product form

- Страница создания/редактирования товара должна быть ориентиром для остальных форм.
- Сейчас финальный стиль ушел от тяжелых рамок: секции должны быть спокойными, с едиными отступами, без лишних бордеров и разделителей.
- Блок подсказок "Что нужно исправить" не показывать, достаточно подсветки полей.
- "Новый товар" не подставлять как дефолтное название.
- Кнопки вариантов:
  - добавление размера/ряда должно быть простым и не ломать структуру вариантов;
  - кнопки удаления должны требовать подтверждение там, где действие необратимое;
  - первый размер нельзя физически удалить так, чтобы форма сломалась, лучше очищать ряд.
- "Фото этого цвета" заменить на "Фото этого варианта".
- Производитель не показывать в форме товара, потому что модель: 1 селлер -> 1 бренд.
- Для активных товаров блокировать отправку на модерацию при изменении цены/остатков, если эти изменения не должны требовать модерации.
- Архивирование и удаление не должны зависеть от несохраненных изменений формы.

### Черновики и загрузка фото товара

- В общем списке товаров не показывать пустые черновики, которые создаются только технически для получения `productId`.
- Как вариант: все черновики вынести из общего списка товаров и показывать их только в отдельном статусе/табе "Черновики" или в отдельном сценарии продолжения редактирования.
- Текущий быстрый MVP-flow может оставаться таким: создать draft -> получить `productId` -> грузить фото через `/api/seller/products/{id}/images`.
- Визуально селлер не должен видеть мусорные пустые товары, если он просто нажал "Добавить товар" и ничего не заполнил.
- Позже добавить очистку заброшенных пустых черновиков или явный сценарий удаления незаполненного draft.

Беклог: временная загрузка фото без товара.

- Backend создает `uploadSessionId` без создания товара.
- Фото грузятся во временное хранилище по `uploadSessionId`.
- При первом сохранении backend создает товар и привязывает временные фото к созданному товару.
- Если селлер бросил форму, временные фото удаляются по TTL/cron.
- Это архитектурно самый чистый production-flow, но для MVP не быстрый, потому что требует отдельного API, временной модели хранения и логики привязки файлов.

## Seller onboarding
