# План проекта RCM

## Главный фокус

Сначала довести фундамент маркетплейса до надежного запуска: товарная модель, checkout, оплата, доставка, СДЭК, возвраты, финансы, модерация, уведомления и базовый UX. После этого расширять рекомендации, аналитику, отзывы, сложные промо-сценарии и красоту вокруг.

Отдельный текущий фокус: не расползаться по точечным UI-решениям. Все новые экраны постепенно приводим к общей дизайн-системе: типографика, кнопки, dropdown, бейджи, карточки списков, кабинетные layout-паттерны, ProductShowcase.

## Текущее состояние

### Уже есть в основе

- Backend и frontend для marketplace flow: товары, каталог, карточка товара, корзина, checkout, заказы, кабинеты покупателя/селлера, админка.
- Product -> Colorway -> SKU заложен в backend: варианты, фото, размеры, цены, остатки, необязательный размер, необязательный артикул продавца.
- Финансовый ledger, комиссии селлеров, snapshot-поля заказа, базовая модель возвратов.
- Checkout считает доставку по seller-группам и ограничивает заказ максимум 3 селлерами.
- Оплата при получении убрана из основного flow, остаются CARD/SBP.
- СДЭК подключен как delivery provider: расчет, ПВЗ, courier/pickup, quote/shipment, polling sync.
- Добавлен `fittingMode`: режим примерки прокидывается в расчет доставки, сохраняется в заказе и отображается в деталках покупателя/селлера.
- Добавлен CDEK webhook foundation:
  - приемник `/api/delivery/cdek/webhook/{secret}`;
  - raw table `cdek_webhook_events`;
  - обработка `ORDER_STATUS`;
  - общий mapper CDEK-статусов для webhook и polling;
  - admin endpoint для создания подписки `ORDER_STATUS` в СДЭК.
- Telegram-уведомления базово готовы: admin/seller события, привязка Telegram у селлера, notification-gateway за пределами РФ.
- Авторизация по телефону и password flow начали заменять старый username-first сценарий.
- На frontend начата общая UI-система: типографика, кабинетные списки, карточки заказов/товаров, product page, мобильное меню, auth modal, seller application.

## Приоритеты

### 1. СДЭК как production-интеграция

Необходимость: 10/10

Ближайшее действие: после подписания договора получить боевые ключи и включить production-режим.

Что нужно сделать после договора:

- получить `CDEK_ACCOUNT`, `CDEK_SECURE_PASSWORD`, `CDEK_SHIPMENT_POINT`;
- выставить на сервере:
  - `CDEK_BASE_URL=https://api.cdek.ru`;
  - `CDEK_DELIVERY_ENABLED=true`;
  - `CDEK_DELIVERY_MOCK_MODE=false`;
  - `CDEK_ACCOUNT`;
  - `CDEK_SECURE_PASSWORD`;
  - `CDEK_SHIPMENT_POINT`;
  - `CDEK_WEBHOOK_SECRET`;
  - `CDEK_WEBHOOK_PUBLIC_BASE_URL=https://rcmarket.io`;
- пересобрать backend;
- создать webhook-подписку через `POST /api/admin/delivery/cdek/webhooks/order-status`;
- проверить полный сценарий: checkout -> оплата -> создание отправления -> webhook status update.

Что осталось по СДЭК:

- проверить реальные статусы СДЭК и при необходимости поправить mapper;
- добавить admin/debug UI для `cdek_webhook_events`;
- обработать `DELIV_PROBLEM`;
- продумать отказ/невручение: `NOT_DELIVERED`, `RETURNED`, client return;
- добавить отмену отправления;
- добавить контроль ошибок создания отправления и понятный retry;
- рассчитывать вес/габариты по товарам, а не только default-пакетом;
- вывести трек-номер/статус понятнее в кабинетах.

### 2. Полный order lifecycle

Необходимость: 10/10

Нужно довести состояния заказа, оплаты, доставки и возврата до единой карты.

Текущие backend-статусы:

- заказ: `NEW`, `CONFIRMED`, `PROCESSING`, `SHIPPED`, `COMPLETED`, `PAID`, `CANCELED`;
- оплата: `PENDING`, `PAID`, `FAILED`, `REFUNDED`;
- доставка: `PENDING`, `READY_FOR_SHIPMENT`, `IN_TRANSIT`, `DELIVERED`, `RETURNED`, `CANCELLED`, `READY_FOR_PICKUP`.

Что нужно:

- убрать неоднозначность между `OrderStatus.PAID` и `PaymentStatus.PAID`;
- финализировать карту статусов для покупателя, селлера и админа;
- зеленые бейджи оставить только для финальных успешных статусов;
- рабочие/нейтральные статусы показывать серым;
- доставку менять от СДЭК webhook/polling, а не руками;
- связать оплату, доставку, возвраты и ledger в единый flow.

### 3. Возвраты, отказы и примерка

Необходимость: 9/10

Базовая модель возвратов уже есть, но нужен полный production-flow.

Принятые правила:

- доставка с примеркой остается;
- покупатель оплачивает доставку с примеркой в checkout;
- если заказ с примеркой частично выкуплен, отдельную обратную доставку за невыкупленное с покупателя не удерживаем;
- если заказ с примеркой полностью не выкуплен без брака/ошибки, товар возвращается, стоимость товаров возвращаем, доставку с примеркой не возвращаем;
- если заказ без примерки и покупатель возвращает товар надлежащего качества, обратная доставка за счет покупателя;
- при браке, неверном товаре, ошибке продавца или сервиса доставку/возврат не перекладываем на покупателя.

Что нужно:

- отразить правила в оферте и пользовательских текстах;
- реализовать сценарии отказа/возврата в backend;
- связать возвраты с ledger;
- добавить статусы возврата и админские действия;
- сделать UI возврата для покупателя, селлера и админа;
- продумать фото/причины возврата и комментарии.

### 4. Финансы и ledger

Необходимость: 9/10

База уже есть: ledger, комиссии, snapshot-поля заказа, admin finance endpoint.

Текущие правила:

- комиссия платформы по умолчанию `20%`;
- индивидуальная комиссия на уровне селлера;
- покупатель видит одну доставку на весь заказ;
- формула доставки: самая дорогая доставка + 50% остальных;
- лимит субсидии доставки: `commissionTotal / 2`;
- если субсидии не хватает, доставка покупателя растет так, чтобы RCM не уходил в минус по прямой доставке;
- максимум 3 селлера в одном checkout.

Что нужно:

- проверить ledger на полном заказе с несколькими селлерами;
- добавить refunds/payouts;
- добавить payout to seller;
- связать ledger с возвратами и отменами;
- сделать admin UI по финансам удобнее;
- подготовить сверку по заказу/селлеру/платежу.

### 5. Product -> Colorway -> SKU

Необходимость: 8/10

Модель уже заложена, теперь задача не “создать с нуля”, а стабилизировать.

Что важно:

- довести связь товар -> вариант/цвет -> размер/остаток/цена/фото до понятного production-flow;
- убедиться, что список товаров, карточка товара, предпросмотр и админка используют одно и то же главное фото;
- не показывать пустые технические черновики в общем списке товаров;
- добавить очистку заброшенных черновиков;
- позже перейти к временной загрузке фото через `uploadSessionId`.

Беклог: временная загрузка фото без товара.

- Backend создает `uploadSessionId`;
- фото грузятся во временное хранилище;
- при первом сохранении backend создает товар и привязывает фото;
- заброшенные фото удаляются по TTL/cron.

### 6. Telegram-уведомления

Необходимость: 8/10

Базовый backend-flow готов.

Уже есть:

- admin-уведомления: новая заявка селлера, новый заказ, товар на модерации;
- seller-уведомления: новый заказ, заявка одобрена;
- привязка Telegram у селлера через `/api/profile/telegram/link`;
- Telegram webhook `/api/telegram/webhook`;
- notification-gateway вне РФ;
- admin test endpoint `/api/admin/telegram/test`.

Что осталось:

- UI подключения Telegram в кабинете селлера;
- UI тестового Telegram-уведомления в админке;
- уведомления по оплате, доставке, возвратам, проблемам доставки;
- outbox/retry/backoff;
- история отправок и диагностика ошибок;
- rate limiting, health, metrics для notification-gateway;
- не блокировать бизнес-операции ошибками Telegram.

### 7. Авторизация по телефону

Необходимость: 8/10

Направление выбрано: телефон становится основным идентификатором.

Что уже сделано:

- flow входа/регистрации по телефону и паролю начал заменять старый username-first;
- регистрация через одноразовый код в dev-режиме может работать с `000000`;
- password flow остается, чтобы не тратить SMS на каждый вход;
- сессии делаем длинными, но не вечными.

Что нужно:

- подключить реального SMS/Mobile ID провайдера: Мегафон или МТС;
- сделать слой-адаптер, не завязывая бизнес-логику на конкретного провайдера;
- rate limit на отправку кодов;
- ограничение попыток ввода кода;
- не возвращать devCode вне local/mock;
- восстановление пароля довести до полного flow;
- аккуратно мигрировать старые username/password аккаунты;
- проверить unique phone constraints на данных.

### 8. Checkout

Необходимость: 8/10

Checkout должен быть одним стабильным flow: данные, доставка, оплата, подтверждение.

Правила:

- Россия по умолчанию;
- ПВЗ выбирается каждый раз, адрес ПВЗ не сохраняем как обычный адрес;
- курьерский адрес не должен перетираться после заказа через ПВЗ;
- при смене города очищаются адрес, квартира, этаж, домофон;
- подсказки адреса/города закрываются кликом вне поля;
- лоадерные тексты типа “ищем адрес”, “рассчитываем” не показываем;
- цена и срок доставки появляются, когда расчет готов;
- `fittingMode` прокидывается в расчет доставки и сохраняется в заказе;
- CARD/SBP остаются основными способами оплаты.

Что нужно:

- проверить полный flow на production-like CDEK/TBank;
- обработать все ошибки оплаты и доставки без 502 для пользователя;
- доработать summary, если будет несколько seller-групп;
- добавить smoke test по checkout.

### 9. Модерация

Необходимость: 7/10

Нужно довести flow товара и предложенных значений.

Статусы товара:

- черновик;
- на модерации;
- опубликован;
- нужны правки;
- архив.

Что нужно:

- комментарий модератора;
- возврат селлеру на доработку;
- предложенные категории/размеры/значения через модерацию;
- не делать отдельный сложный раздел раньше времени, если действие можно делать в деталке товара;
- добавить журнал действий админа.

### 10. Админка

Необходимость: 7/10

UI админки уже начали приводить к общему стилю, но нужна функциональная диагностика.

Ближайшее:

- просмотр `cdek_webhook_events`;
- просмотр статусов отправлений и ошибок СДЭК;
- удобный finance ledger;
- возвраты;
- заявки селлеров;
- товары на модерации;
- словари категорий/размеров/аудитории;
- убрать цвета из основного UI админки, пока фильтры по цвету не нужны.

Mobile для админки: не делать идеальный мобильный кабинет первым делом, но основные карточки должны открываться и не ломаться.

### 11. UI-система и frontend

Необходимость: 7/10

Общие договоренности:

- UI простой, спокойный, fashion/ecommerce, без лишних пояснений;
- основные цвета: черный, белый, золото;
- gold palette:
  - `--gold`;
  - `--gold-muted`;
  - `--gold-deep`;
  - `--warning`;
- black/grey palette нужно компактно унифицировать;
- карточки списков заказов/товаров должны иметь общий паттерн;
- кнопки, dropdown, поля, бейджи, таббары и сайдбары нужно свести к общим компонентам;
- текстовые роли фиксируем и применяем постепенно;
- кнопкам нужен отдельный стиль `textButton`;
- SVG icon set вынести отдельно.

Ближайшее по UI:

- ProductShowcase как общий компонент:
  - grid-подборка на 4 товара;
  - carousel для карточки товара/корзины;
  - mobile horizontal scroll + indicator;
- карточка товара как эталон product UI;
- кабинеты покупателя/селлера и админка в одном layout-ритме;
- auth modal и seller application в дизайн-системе;
- catalog mobile: 2 карточки в ряд, компактные actions, аккуратная типографика.

### 12. Поиск, фильтры, рекомендации

Необходимость: 6/10

После стабилизации заказов и доставки.

Нужно:

- фильтры по размеру, бренду, цене, наличию, аудитории;
- цвет/варианты позже, когда модель в UI окончательно стабилизирована;
- SQL + индексы на первом этапе;
- позже Elasticsearch/OpenSearch;
- подборки:
  - “Еще от бренда”;
  - “Похожие в категории”;
  - “Недавно просмотренные”;
  - рекомендации позже, когда будет понятна логика.

### 13. Seller analytics, отзывы, вопросы

Необходимость: 5/10

Не блокирует первый запуск.

Позже:

- оборот;
- количество заказов;
- товары к отправке;
- популярные товары;
- остатки;
- конверсия;
- отзывы;
- вопросы к товару.

## Ближайшие крупные действия

1. Подписать договор со СДЭК, включить production CDEK и проверить полный shipment lifecycle.
2. Добавить admin/debug просмотр `cdek_webhook_events` и ошибок отправлений.
3. Прогнать полный order flow: checkout -> payment -> shipment -> webhook -> кабинеты.
4. Довести возвраты/отказы/примерку до рабочего backend + UI flow.
5. Проверить ledger на заказах с несколькими селлерами, возвратами и доставкой.
6. Довести auth по телефону до production: SMS/Mobile ID, rate limits, восстановление пароля.
7. Закрепить UI-систему: кнопки, dropdown, бейджи, typography, ProductShowcase, icons.
8. Продолжить шлифовку кабинетов, админки, карточки товара и checkout.
9. Подготовить юридические тексты: оферта, возвраты, доставка, обработка персональных данных.
10. Перед релизом ротировать все секреты и пройти `PRELAUNCH_TESTING_PLAN.md`.

## Перед запуском

- Все реальные ключи только в env, не в git.
- Ротировать секреты, которые светились в чатах/терминалах.
- Пройти smoke test на production-like конфиге.
- Проверить платежи, возвраты, доставку, уведомления, админские действия.
- Проверить мобильный checkout и карточку товара.
- Проверить юридические тексты и публичные правила доставки/возврата.
