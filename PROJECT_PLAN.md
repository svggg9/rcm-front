# План проекта рцмаркет

> Дополнение 19 сентября после запроса на серверную выкладку: frontend и backend обновлены на test и production, обе БД — V99, приложения healthy. Пройдены 340 unit/web + 24 integration backend, сборки обоих frontend и smoke. См. [отчёт релиза](DEPLOYMENT_2026-09-19.md). Это заменяет прежние пометки «не выложено / сборки отложены» для переданного снимка; бизнес-E2E и функциональный backlog остаются открытыми.


Актуализирован 19 сентября 2026 по рабочим исходникам frontend `main` и backend `master`.
Основное рабочее место — Windows. Передача: [WINDOWS_HANDOFF.md](WINDOWS_HANDOFF.md).
Git-публикация исходников не означает выкладку приложения на test/production.

## Текущее состояние

- Frontend: Next.js 16 / React 19 / TypeScript. Backend: Spring Boot 4.1.1 / Java 21, PostgreSQL, Redis, Flyway. Notification gateway входит в backend-репозиторий.
- Реализованы основные товары/варианты/SKU, каталог, корзина, checkout, кабинеты, модерация, оплата, доставка, возвраты и ledger. Полная готовность этих сценариев к production ещё не подтверждена.
- Изменения 8–10 сентября включают публичные страницы и бренд «рцмаркет», мобильную навигацию покупателя, каталог, корзину, checkout, кабинеты и общие UI-компоненты.
- У продавца отдельная чёрная шапка и двухуровневая навигация без счётчиков: Обзор / Каталог / Заказы / Финансы / Магазин / Данные и документы. Подразделы находятся вторым рядом; создание товара/подборки — у поиска и фильтров.
- Редактор товара открывается панелью поверх списка через parallel/intercepted routes; прямая ссылка сохранена. Подборка — компактный диалог; на мобильном полноэкранный редактор. Есть закреплённые действия и подтверждение потери несохранённых правок.
- Добавлены массовые действия с товарами, сортировка, добавление в подборки, предварительный просмотр товаров заказа, общие формы/ошибки/диалоги. Полный ручной аудит всех состояний ещё нужен.
- Backend: добавление товаров в подборку с проверкой владельца и блокировкой, разрешённые поля сортировки товаров, article/createdAt в списке, исправления фильтров каталога, русские ошибки публикации, миграции категорий V95–V99, соответствующие тестовые исходники.
- Восстановление пароля реализовано в обеих частях. Это не реализация входа через email OTP: frontend всё ещё обращается к `/api/auth/email/login/start` и `/complete`; согласованного backend-контракта для них нет.
- В текущем backend `master` отмена вызывает `cancelPaidOrder`; ручную отмену неоплаченного заказа и TTL резервов нельзя считать закрытыми по старым веткам или наличию UI.

## Согласованные правила интерфейса

Источники: [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), `/design-system` в dev, текущие рабочие компоненты. Последние уточнения имеют приоритет над историческими разделами документа.

- Чёрный / белый / золото, спокойный интерфейс без лишних пояснений.
- Текущий шрифт в `app/layout.tsx` — Inter; не возвращать прежние эксперименты со шрифтами без нового решения.
- Не возвращать счётчики во вкладки и отдельную дублирующую навигацию продавца.
- Переиспользовать формы, кнопки, статусы, диалоги и иконки дизайн-системы; сохранять доступные названия действий.
- Демонстрационные страницы не равны полностью завершённому переносу во все экраны.

## Ближайший порядок работ

1. **Восстановить работу на Windows.** Забрать оба репозитория, подготовить локальные env и изолированные PostgreSQL/Redis, запустить frontend/backend по инструкции передачи. Проверить доступность основных страниц. Не переписывать работающие модули при переносе.
2. **Закончить текущий frontend.** Проверить двухуровневое меню, товары/подборки, сортировку и пагинацию, массовые действия, панель товара, прямой URL/refresh/back, dirty-close, вложенные диалоги и мобильные ширины 320/390/1280. Поиск заказов сейчас фильтрует загруженную часть списка; не считать его глобальным серверным поиском.
3. **Согласовать критичные API-контракты.** B1/B2 backend-плана: TTL неоплаченного заказа, освобождение резерва, ручная отмена, поздняя оплата, допустимые действия и статусы заказа. Правила TTL/поздней оплаты требуют продуктового решения. B3: скрыть неподдерживаемый OTP либо отдельно реализовать его после согласования.
4. **Довести интеграции и эксплуатацию.** B4/B5: повторные webhook, потерянные ответы, безопасные повторы, ошибки доставки/оплаты/возвратов и наблюдаемость. Затем минимальные уведомления покупателю B6 и аудит дублей email B7.
5. **Общий приёмочный прогон после завершения frontend.** Сборки frontend/backend, unit/integration и [PRELAUNCH_TESTING_PLAN.md](PRELAUNCH_TESTING_PLAN.md): оплата, доставка, отмены/возвраты, несколько продавцов, ledger, права, восстановление пароля, мобильные сценарии. Только изолированные тестовые данные/хранилище.
6. **Отдельный релиз.** Проверить production-конфигурацию, секреты, Redis/proxy, S3 isolation, backup/rollback, полные SHA и артефакты сборки. Выкладка и реальные провайдеры — отдельный этап.

Детальная backend-очередь — `BACKEND_PLAN.md` в `svggg9/rcm`.
Аналитика, отзывы, рекомендации и сложные промо не блокируют первый запуск.
Юридические тексты остаются отдельным предрелизным блоком, а не задачей текущего переноса.
