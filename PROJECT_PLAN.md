## Алерты корзины без зависания — 13 октября 2026

Причина накопления старых ошибок — duration: Infinity в общей обёртке toast.error. Ошибки теперь исчезают через 4 секунды, как остальные уведомления; явные настройки конкретных операций сохранены. Добавление из карточки/избранного использует один ID ошибки на товар и экран, обновляет прежний алерт при повторном отказе, очищает при успехе и уходе с экрана. Перед повторным запросом ID не закрывается: иначе анимация удаления Sonner могла удалить уже обновлённую ошибку быстрого ответа. Успешный серверный ответ изменения/загрузки корзины сбрасывает устаревшие ошибки действий и временные ограничения остатков. Реальное превышение пяти единиц продолжает вычисляться из актуального состава и блокирует оформление до исправления. Текст остаётся «Не больше 5 единиц одного товара»; старый полный ответ backend нормализуется на frontend.

Проверки: check-toast, check-cart, check-cart-checkout (ошибка одного размера → уменьшение другого, обновление остатков, настоящее превышение → исправление), lint и TypeScript. В изолированном браузерном fixture проверены короткий текст, автоматическое исчезновение в карточке/избранном, один алерт после повторных попыток и очистка при переходе. Мобильный пример — build/cart-alerts/limit-alert-390.png; рабочая корзина/БД и backend не менялись. Это локальное исправление, без выкладки; уже созданные бесконечные уведомления удаляются обновлением страницы.

## Смена почты с двумя подтверждениями — 13 октября 2026

Профиль всегда открывается readOnly. Только «Редактировать» включает имя/фамилию/телефон и показывает действия смены почты/пароля. Смена email встроена в страницу: код на текущий адрес → ввод нового адреса → код на новый → немедленная замена подтверждённого email. Обычное сохранение профиля не меняет email. Незавершённая смена защищена InlineEditorGuard; повторная отправка имеет countdown, запросы — single-flight, ошибки безопасные. Подтверждение текущей почты хранится только в памяти страницы, не в localStorage.

Backend /api/profile/email-change/** требует авторизацию и прежнюю проверку Origin. Purpose-separated Redis-коды: 10 минут, 5 ошибок, повтор через 60 с, лимиты по IP/identity; короткоживущий capability привязан к id/старой почте/tokenVersion. Только оба подтверждения меняют email, версия сессий увеличивается; текущая cookie обновляется, остальные сессии прекращаются. Внутренний username и ключ корзины сохраняются. Если notificationEmail совпадал со старым основным адресом, он тоже заменяется; отдельный альтернативный адрес не меняется. V115 добавляет unique index нормализованного подтверждённого email; перед серверной выкладкой нужен аудит существующих дублей, автоматического объединения аккаунтов нет.

Проверки: 7 новых integration PostgreSQL/Redis (два кода, чужой proof, чужой адрес, истечение proof, лимиты, отказ SMTP, отзыв старой cookie/обновление текущей, конкурентный захват email), 8 EmailLoginIntegrationTest; выбранные auth unit/web прошли. Для MVP одна VM на 8 GiB выглядит приемлемым временным размещением: у test/prod отдельные приложения и БД, но общие VM, ресурс и отказ. Эталон перед реальными продавцами — разнести test и prod по разным VM и сохранить раздельные БД/секреты; перенос test на отдельную VM добавит стоимость и обслуживание. Пользователей пока нет, поэтому отдельная VM сейчас не обязательна. Выбор 8 GiB исполнен владельцем. 18 октября владелец прислал read-only снимок: UFW inactive; `ss -lntp` показывает публичные IPv4 listeners SSH :22 и nginx :80/:443. Docker app/DB host ports привязаны к loopback: test frontend :3200, prod :3000, test backend :9896, prod :9696, prod PostgreSQL :25432; test PostgreSQL и оба Redis не опубликованы на host. Nginx active, `nginx -t` успешен. Это подтверждает listeners и валидность синтаксиса nginx, но не правила облачной security group, эффективный nftables ruleset, доступность upstream/сертификатов или безопасные настройки TLS. UFW inactive сам по себе не доказывает отсутствие cloud filtering. Эталон: извне доступны только 80/443; SSH ограничен доверенным адресом администратора, apps/БД/Redis снаружи не доступны. В Yandex Cloud нужно проверить все security groups на интерфейсе VM: default group разрешает весь входящий IPv4, а разрешения нескольких групп складываются. Далее — сверить группы и `sudo nft list ruleset`; правила пока не менялись. Memory limits остаются невыбранными. I1 открыт.
