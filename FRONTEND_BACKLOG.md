### Исходный анализ

Пользователь выбрал frontend и запросил сначала анализ/согласование. Код не менялся. Подтверждено чтением:

- `favoriteBrands.ts`: неуспешный GET и некорректный успешный ответ становятся пустым списком; сеть/ошибка JSON не получают собственного состояния ошибки. Toggle передаёт сырой response.text в Error, а оба потребителя показывают error.message в toast.
- `sellerBrandApi`, сохранение реквизитов, действия возвратов и общий adminApi также используют сырой ответ. `sellerNotificationApi` доверяет произвольному message/error из JSON. Эти места требуют проверки пути до UI при реализации соответствующего модуля.
- Вход, checkout и accountApiError уже имеют словари известных сообщений и безопасный fallback; их специфические бизнес-решения сохраняем. Общий apiFetch сейчас только выполняет запрос; не добавлять в него глобальные toast, переходы или автоматические повторы мутаций.
- `client-session.ts` считает любой неуспешный HTTP-ответ отсутствием сессии и кеширует null. Контракт AuthController различает 200 (пользователь) и 204 (гость). Сбой 5xx не должен превращать пользователя в гостя. Через cartAuthority это может выбрать гостевую корзину. Это отдельный критичный подпункт H02: перед изменением проверить всех потребителей сессии, включая useCurrentUser, корзину и избранное; не ограничиваться выбросом Error без UI-обработки.
- `loadResolvedCartCount` возвращает 0 при отказе API: при разборе корзины отличить подтверждённый ноль от неизвестного счётчика. Ошибка не должна сама менять подтверждённый состав/сумму/счётчики.

Согласованные правила: общий безопасный разбор HTTP/сети/таймаута/невалидного ответа, известные коды → согласованный русский текст, неизвестное → контекстный fallback. Ошибка поля возле поля, сбой загрузки в соответствующем блоке с повтором, ошибка короткого действия — один toast на 4 секунды с откатом неподтверждённого изменения. Существующие данные/ввод сохраняются, обновление блокируется только в конфликтующем действии. Отмена запроса при уходе не показывается как ошибка. При неизвестном результате оплаты/создания/возврата сначала проверять факт выполнения; не обещать, что действие точно не выполнилось, и не повторять автоматически.

Согласованная последовательность: общая основа + «Мои бренды» (реализовано) → отдельный блок проверки сессии и её потребителей (следующий) → остальные сценарии покупателя/корзины → продавец/возвраты → админка. Остающийся риск session 5xx явно не считать закрытым исправлением GET брендов. Технический HTTP-статус сам по себе не задаёт бизнес-состояние: 404/409 и 401 обрабатываются с учётом конкретного запроса, без глобального logout/redirect.

Проверки для будущей реализации: настоящий пустой список, 5xx с JSON/HTML, сеть/таймаут, невалидный успешный ответ, успешный повтор, неудачный toggle, уход/смена аккаунта во время запроса, отсутствие дублей уведомления и сброса других успешных действий. На этом этапе выполнен статический анализ, браузерное воспроизведение и новые тесты не запускались; backend менять для первого блока не требуется.
