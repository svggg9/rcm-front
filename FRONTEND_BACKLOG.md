# Единая очередь проекта и отложенные задачи

## Выход и смена пароля — 7 ноября 2026, локально

Выход ожидает подтверждения сервера, сохраняет кабинет при неизвестном результате
и очищает текущий черновик заказа после успеха. Профиль уточняет, что ответ на
запрос восстановления не подтверждает доставку письма. Прямой backend маршрут
смены пароля дополнительно ограничен по аккаунту/IP; UI использует отдельный
email reset с существующими лимитами. Адресные frontend fixtures, lint и
TypeScript PASS, backend unit/Redis integration PASS; browser E2E и реальная
доставка почты не проверялись. Серверы не обновлялись.
[Детали и ограничения](../../rcm/PASSWORD_CHANGE_PROTECTION_2026-11-07.md).

## Публичные rate limits и ошибки — 7 ноября 2026, локально

Подключён UI-контракт публичных 429/503/Retry-After: поиск городов сохраняет
query/подтверждённые данные и показывает безопасную ошибку в существующем поле.
Yandex получает authorizationUrl через новый JSON `/api/auth/yandex/start-url`,
проверяет HTTPS/provider host и использует прежнюю AuthForm для ошибок.
Денежные mutation unknown-result/retry правила сохранены. Newsletter/product-preview
пока не вызываются frontend, новые формы не добавлены.

5 offline regression scripts, полный lint, TypeScript, contract:check и production
build PASS (`build/public-api-protection-20261107`); реальная OAuth-приёмка и выкладка не выполнялись. Backend
нужно выкладывать первым, frontend после него. ADMIN/MFA отложена владельцем,
первичный вход/поля и logout не менялись. Подробности — [PROJECT_PLAN](PROJECT_PLAN.md).

## Диагностика операций — 7 ноября 2026

Локально добавлен блок ADMIN overview с подсказками для сверки платежей,
возвратов и доставки; серверная фильтрация и права — в
[backend контракте](../../rcm/ADMIN_OPERATION_ALERTS_API.md). Переход к конкретному
заказу сохранён. Браузерную визуальную проверку выполнить после восстановления
доступа Computer Use; реальные платежи/возвраты/СДЭК этим блоком не принимались.
Для конкретного возврата есть прямой переход; в очередях оплат и возвратов
заблокированы действия по устаревшим данным, а неопределённый результат операции
сопровождается требованием сверить состояние перед повтором. Изолированные ESLint,
TypeScript и проверки контрактов/сценариев прошли.

## Единый план MVP и развития — 7 ноября 2026

Источник — текущий запрос владельца в чате «Проверить реальный заказ на проде (2)»:

риск денег/данных/доступов, основной путь покупки и зависимости. Старые задачи

Q15–Q27 детализируют ранее общие предложения. Факты реализации/проверок —
[PROJECT_PLAN](PROJECT_PLAN.md) и [BACKEND_PLAN](../../rcm/BACKEND_PLAN.md).

### Приоритет и закрытие

- **P0 — обязательно до публичного MVP:** результат нужен для безопасного основного
  сценария; исключение требует явного согласованного ограничения первого запуска.
- **P1 — после пилота/до привлечения трафика:** не блокирует первую контролируемую
  покупку. Допустимо делать параллельно P0, особенно уже порученное в другом чате.
- **P2 — по спросу/нагрузке:** стартует при появлении указанного бизнеса.
- «Код есть», «локально проверено», «внешняя приёмка открыта», «ожидает решения/
  данных», «делается в другом чате», «выложено и принято» — разные статусы.
  PASS содержит версию/среду и фактический результат; для денег — сверку банка,
  остатков/ledger/чеков. MOCK/fixture/HTTP200 не заменяет внешнюю приёмку.
  Невоспроизведённый внешний случай остаётся открытым с конкретной причиной.

### Последовательность работы с хвостами

1. Параллельно получить решения Q14.1 и подготовить кандидат/проверочный набор Q02.
   Пока нужны внешние данные, делать независимые Q06.1/Q15.1 и проверку Q08.1.
2. После доступности SMTP/банка/кассы: Q05 → Q03 → Q04.1 и внутренние refunds;
   после готовности обратной доставки закрыть полный Q07 → Q09.1/Q13.1.
   Исправления общих компонентов из соседнего чата включать в тот же кандидат.
3. Q11 и финальный Q02 закрывают публичный MVP. Новый дефект денег, потери данных
   или прав становится P0 независимо от возраста. Каждый хвост завершается proof
   по версии/среде либо точной открытой зависимостью, а не повторной реализацией модуля.

### Исходный анализ

Пользователь выбрал frontend и запросил сначала анализ/согласование. Код не менялся. Подтверждено чтением:

- `favoriteBrands.ts`: неуспешный GET и некорректный успешный ответ становятся пустым списком; сеть/ошибка JSON не получают собственного состояния ошибки. Toggle передаёт сырой response.text в Error, а оба потребителя показывают error.message в toast.
- `sellerBrandApi`, сохранение реквизитов, действия возвратов и общий adminApi также используют сырой ответ. `sellerNotificationApi` доверяет произвольному message/error из JSON. Эти места требуют проверки пути до UI при реализации соответствующего модуля.
- Вход, checkout и accountApiError уже имеют словари известных сообщений и безопасный fallback; их специфические бизнес-решения сохраняем. Общий apiFetch сейчас только выполняет запрос; не добавлять в него глобальные toast, переходы или автоматические повторы мутаций.
- `client-session.ts` считает любой неуспешный HTTP-ответ отсутствием сессии и кеширует null. Контракт AuthController различает 200 (пользователь) и 204 (гость). Сбой 5xx не должен превращать пользователя в гостя. Через cartAuthority это может выбрать гостевую корзину. Это отдельный критичный подпункт H02: перед изменением проверить всех потребителей сессии, включая useCurrentUser, корзину и избранное; не ограничиваться выбросом Error без UI-обработки.
- `loadResolvedCartCount` возвращает 0 при отказе API: при разборе корзины отличить подтверждённый ноль от неизвестного счётчика. Ошибка не должна сама менять подтверждённый состав/сумму/счётчики.

Согласованные правила: общий безопасный разбор HTTP/сети/таймаута/невалидного ответа, известные коды → согласованный русский текст, неизвестное → контекстный fallback. Ошибка поля возле поля, сбой загрузки в соответствующем блоке с повтором, ошибка короткого действия — один toast на 4 секунды с откатом неподтверждённого изменения. Существующие данные/ввод сохраняются, обновление блокируется только в конфликтующем действии. Отмена запроса при уходе не показывается как ошибка. При неизвестном результате оплаты/создания/возврата сначала проверять факт выполнения; не обещать, что действие точно не выполнилось, и не повторять автоматически.

Согласованная последовательность: общая основа + «Мои бренды» (реализовано) → отдельный блок проверки сессии и её потребителей (следующий) → остальные сценарии покупателя/корзины → продавец/возвраты → админка. Остающийся риск session 5xx явно не считать закрытым исправлением GET брендов. Технический HTTP-статус сам по себе не задаёт бизнес-состояние: 404/409 и 401 обрабатываются с учётом конкретного запроса, без глобального logout/redirect.

Проверки для будущей реализации: настоящий пустой список, 5xx с JSON/HTML, сеть/таймаут, невалидный успешный ответ, успешный повтор, неудачный toggle, уход/смена аккаунта во время запроса, отсутствие дублей уведомления и сброса других успешных действий. На этом этапе выполнен статический анализ, браузерное воспроизведение и новые тесты не запускались; backend менять для первого блока не требуется.

Предложение уточнено: на мобильном отдельный корневой экран профиля со строками меню и тонкими разделителями; внутри раздела стрелка назад и центрированный заголовок; в заказе номер и копирование. Прежнее предложение стартовать сразу с заказов и использовать выпадающий переключатель уступает этому варианту, окончательная структура ещё согласуется. На desktop компактное боковое меню сохраняется.

Предложенные наши строки: имя/личные данные, заказы, возвраты, избранное, мои бренды, адреса при наличии полноценного сценария; помощь, кабинет продавца и выход отдельной группой. QR/магазины/регион/рассылка не копируются без нашей функции. Личные данные — просмотр значений, затем явное редактирование с сохранением существующих защит смены контактов. Список — короткая шапка, фото и количество/сумма; деталка — доставка, реальный прогресс, товары, способ оплаты, суммы (включая отдельную доставку), доступный возврат. Точные даты этапов показывать только при наличии API-данных, без вычисления из текущего статуса. Footer на мобильном кабинете остаётся предложением к отдельному решению: на скринах Lime он есть в профиле, это не основание автоматически копировать или скрывать его везде. Персональные значения со скриншотов в документацию не переносятся.
