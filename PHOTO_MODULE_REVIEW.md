# Фотографии — оценка модуля, 6 октября 2026

Основание: чтение текущих frontend `main` и backend `master` с сохранёнными
параллельными изменениями, адресные проверки новой обработки и UI галереи бренда.
Это локальная оценка; полный бизнес-E2E, нагрузка и рабочее cloud S3 не проверены.

Модуль функционально развит: загрузка, перестановка, главное фото и цвета товаров,
предпросмотр бренда, подтверждение удаления и ограничения владельца уже есть.
Главный оставшийся пробел — согласованность записей БД и файлов при замене,
копировании и сбоях. Политики обработки должны различаться по назначению фото.

## Реализовано в этом блоке

Новые JPEG/WebP галереи бренда до 8 МиБ преобразуются на backend до записи в S3:
длинная сторона до 2400 px, без увеличения, EXIF-поворот/зеркалирование,
прозрачность сохраняется, исходные метаданные удаляются. Принимается одна статичная
фотография, проверяются целостность, содержимое, предел 48 MP и 16384 px по стороне.
Одновременно обрабатывается один растр; при занятости возвращается 503 с повтором.

WebP quality 88→84→80→78. Мягкая цель — минимум из 500 КиБ и веса исходника;
ниже качества 78 обработчик не опускается. Вес 300–500 КБ — ориентир, не контракт:
простой кадр может быть меньше, сложный — больше, диагностический шум может
оказаться тяжелее исходника. Тесты проверяют параметры; оценка качества двух
реальных кадров визуальная, без заявления об отсутствии потерь.

Новый объект удаляется при откате БД; удаление существующего файла происходит
после commit удаления записи. Сбой S3 cleanup логируется и не меняет результат БД;
устойчивой очереди повторов очистки пока нет. Уже сохранённые фото не переписываются.

Frontend проверяет MIME/пустоту/8 МиБ до запроса, отправляет исходный файл,
показывает понятные ошибки API и поясняет автоматическое уменьшение.
Кликабельная пустая галерея и плитка добавления сохранены.
Код: [API загрузки](app/seller/lib/sellerBrandApi.ts),
[галерея бренда](app/seller/components/SellerBrandImages.tsx).
Backend: `storage/BrandGalleryImageOptimizer`, `storage/FileStorageService`,
`brand/BrandImageService`; решение — `docs/knowledge/ADR-004 — Оптимизация фото бренда.md`.

Windows и Java 21/Linux glibc x64 дали одинаковые SHA256 WebP для всех четырёх.
ARM64/musl и серверная нагрузка не проверялись. Локальные before/after и JSON
измерений находятся в игнорируемом backend `build/photo-opt-check`.

## Что уже сделано хорошо

- Backend проверяет роль и владение; загрузки бренда/товара ограничены по количеству
  под блокировкой. Бренд — до 8, товар — до 10 фото; 3–10 и минимум 1200 px по короткой
  стороне проверяются при модерации. Малые товарные оригиналы допустимы в черновике
  по [требованиям](PRODUCT_PHOTO_REQUIREMENTS.md), без автоматического увеличения.
- SVG имеет статический allowlist и защиту XML-парсера; URL удаления S3 проверяет
  origin/порт/bucket и traversal. Фото возвратов выдаются через защищённый API
  с private/no-store/nosniff; совместимая выкладка этой локальной правки ещё нужна.
- Публичные изображения используют `Next/Image` и `sizes`; второе фото плитки
  загружается по намерению пользователя. Интерфейсы блокируют повторные мутации
  и спрашивают подтверждение удаления.
